四遍的代码

这是「反思（Reflection）」范式的原始速写：让同一个模型扮演程序员与评审员， 反复读稿、挑刺、重写。下面这份记录来自一次真实运行——四个版本、三轮评审， 其中第三版被评审自己推翻。它比任何示意图都更能说明这个循环的脾气。

模型 deepseek-flash 调用 7 次（1 初始 + 3 反思 + 3 优化） 轮次 max_iterations = 3 结果 奇数筛 · O(n log log n)
01

改稿轨迹：从朴素筛到「绕回来的筛」

v1

初始尝试：标准埃氏筛

R1 → 改

模型直接给出全长度筛，用 bytearray 加切片赋值，代码干净。

sieve = bytearray([1]) * limit          # 为全部整数建筛
sieve[0:2] = b"\x00\x00"
for i in range(2, int(limit ** 0.5) + 1):
    if sieve[i]:
        sieve[i*i:limit:i] = b"\x00" * count
该代码已采用埃氏筛，时间复杂度 O(n log log n)，算法层面已属渐进最优； 但存在实现层面的常数因子瓶颈：偶数冗余、切片临时内存、int(limit ** 0.5) 的浮点风险。

评审给了五条微观优化建议，全部指向「减少一半工作量」，于是有了 v2。

v2

采纳「奇数筛」

R2 → 改

只表示奇数，内存与迭代次数各减半；顺手把浮点开方换成精确的 math.isqrt。

size = (limit + 1) // 2          # 只存奇数，长度减半
sieve = bytearray(b"\x01") * size
root = math.isqrt(limit - 1)         # 精确开方，无浮点误差
sieve[start::p] = b"\x00" * count        # 仍是 C 层切片，快
已在算法上最优；但可再进一步：2,3,5-wheel 可减少约 1/3 的筛除操作， 切片赋值仍有临时分配，建议考虑 wheel factorization 与向量化提取。

这条建议把方向从「常数优化」推向了「重构数据结构」，于是有了 v3。

v3

采纳「2,3,5-wheel」——过度走火

R3 → 推翻

为了只表示与 30 互质的数，代码引入了残差表、wheel 索引映射和手写步进循环，从 30 行膨胀到 100 多行。

residues = (1, 7, 11, 13, 17, 19, 23, 29)
wheel = ((0,0,0,0,0,0,0,0), (1,7,3,5,2,6,4,0), …六行查表…)
while cur < limit:                       # 用 Python 循环模拟 wheel 步进
    idx2 = (cur // 30) * 8 + cur_ri
    cur += p * gap; cur_ri = next_ri
当前代码在算法层面并非最优：wheel 的 Python 循环实现引入了大量常数开销， 实际性能不如简洁的奇数筛配合切片赋值，建议退回。标准筛可以把主要工作交给 C 层切片， 而这里每一步都在解释器里跑。
REVERTED

三轮里最反直觉的一幕：评审把自己上一轮的建议推翻了。

v4

回退：更简洁的奇数筛

达到上限 · 采用

结构回到 v2，但写法更紧：位移代替除二、索引与步长都省一次算术。

size = (limit + 1) >> 1
sieve[start::step] = b"\x00" * count   # 批量置零交给 C
return [2] + [(i << 1) + 1 for i in range(1, size) if sieve[i]]

循环在 range(max_iterations) 走完后自然结束，没有触发「无需改进」。 最终答案就是 v4 的全部代码。

这段轨迹本身就是一个结论：反思循环没有「目标函数」。评审员每一轮都能找出新缺点， 于是代码可能震荡——先因「不够快」变复杂，再因「太复杂」变简单。 这次运气不错，落脚点是对的；但换成别的题，第四版完全可能比第一版更差。
02

结构：三个角色，三张模板

整个类只有 40 行有效代码，却由三个互相咬合的部分组成：记忆、循环、取文本。

CLASS

Memory

一个 list[dict] 的包装，记录类型只有两种：execution（代码）与 reflection（评审意见）。

提供两个读取视角：get_trajectory() 拼成长文本、get_last_execution() 倒序找最近一版代码。

CLASS

ReflectionAgent

run() 负责节拍：先跑一次初始尝试，再进入 reflect → 判停 → refine 的循环。

判停依据是字符串匹配：反馈里出现「无需改进」就 break。

METHOD

_get_llm_response()

唯一的出口。把 prompt 包成单条 user 消息丢给 think()，用 or "" 兜住空响应。

三个调用点全走它，所以想换模型、加温度、加日志，只改这一处。

三张模板，各管一件事

模板被谁用关键要求
INITIAL_PROMPT_TEMPLATE 首次写代码 完整签名 + 文档字符串 + PEP 8；只输出代码，不许解释
REFLECT_PROMPT_TEMPLATE 每轮评审 只看算法效率；要求分析时间复杂度；算法已最优才准说「无需改进」
REFINE_PROMPT_TEMPLATE 每轮重写 必须带着「上一版代码 + 评审反馈」一起改写，不许重起炉灶
评审模板里限定「只谈算法效率」，是为了避免模型纠结节风格、变量名。 这次运行也验证了这条约束有效：三轮意见全部围绕复杂度与常数因子，没有一句在说命名。 但也正是「必须找问题」的设定，逼出了 v3 那种过度优化。
03

执行流程：一次外循环，一次内循环

  1. 初始尝试 · 先拿到一份「能跑的草稿」

    run() L104–L108 · add_record("execution", initial_code)

    不等评审、不看历史，直接按任务写第一版。这一步确保循环永远有一个可批评的对象。

  2. 进入循环 · 每轮都是一个「读—评—改」

    for i in range(max_iterations)

    轮次编号只用于打印，不参与任何逻辑；真正决定结束的是第 4 步的字符串匹配。

  3. 反思 · 只看最近一版代码

    L116–L119 · get_last_execution() + REFLECT_PROMPT_TEMPLATE

    取 最近一条 execution，而不是全部历史。所以评审员看到的是「当前稿」，不看你的改稿史——这也解释了 v3 为什么敢推翻 v1 的前提。

  4. 判停 · 反馈里是否出现「无需改进」

    L122–L124 · if "无需改进" in feedback: break

    唯一的提前退出条件。本次三轮都没出现这四个字，所以跑满了上限。

  5. 优化 · 带着反馈重写，而不是重写全部

    L128–L134 · REFINE_PROMPT_TEMPLATE → add_record("execution", …)

    prompt 里同时给了原始任务、上一版代码、评审意见，约束模型「按意见改」。新版本重新进入第 2 步。

  6. 收尾 · 最后一版即答案

    L136–L138 · return final_code

    循环结束后再取一次 get_last_execution()，打印并返回。没有「综合所有版本」的步骤——最新的那份就是最终稿。

04

记忆里到底存了什么

Memory.records 是整条流水线唯一的持久状态。本次运行结束时它长这样（共 7 条）： 

[
  {"type": "execution",  "content": "```python\ndef get_primes_below(...)  # v1 全筛"},
  {"type": "reflection", "content": "算法已最优，但偶数冗余、切片临时内存…"},
  {"type": "execution",  "content": "…  # v2 奇数筛"},
  {"type": "reflection", "content": "建议 2,3,5-wheel + 向量化提取…"},
  {"type": "execution",  "content": "…  # v3 wheel 实现"},
  {"type": "reflection", "content": "wheel 的 Python 实现开销巨大，建议退回…"},
  {"type": "execution",  "content": "…  # v4 奇数筛（终稿）"}
]
读取方式返回被谁用用途
get_last_execution()str | None反思、收尾倒序遍历，取最近一条 execution
get_trajectory()str当前未被调用把全部记录拼成「改稿史」文本
add_record()None循环内两处写入并打印「记忆已更新」
一个现成的改造点：get_trajectory() 已经写好了，但 run() 里没有任何调用。 如果把它的输出塞进 REFINE_PROMPT_TEMPLATE，评审员就能看到「你上一轮建议过什么、结果如何」， v3 那种来回震荡大概率能减少。
05

四个边界条件

  • 停止靠字符串：if "无需改进" in feedback。评审员换个说法（「已是最优」「无明显瓶颈」）就匹配不到， 只能跑满 max_iterations。本次即如此——第三轮意见里出现的是「并非最优」。
  • 评审只看代码，不跑代码：整个流程没有 exec()、没有测试、没有计时。 v3 到底快不快，全凭模型「读」出来的直觉。它这次读对了，但机制上没有任何保证。
  • 空响应被静默降级：think(...) or "" 把 None 变成空串， 后续 split、in 都不会崩，但会得到一版空代码，且没有任何告警。
  • 可选项未收紧：get_last_execution() 返回 Optional[str]， 传给 .format() 前已加 or ""，否则会把字面量 "None" 拼进提示词。

一个纯装饰性的瑕疵

最终打印时会看到两层围栏： 

--- 任务完成 ---
最终生成的代码:
```python          ← run() 自己加的一层
```python          ← 模型返回内容自带的一层
import math
…

原因：模型输出本身已含 ```python 围栏，run() 打印时又包了一次。 修法二选一：在 _get_llm_response() 里剥掉围栏，或打印时不再额外包。

06

这个范式值得记住的三件事

一、它是「审稿会」，不是「编译器」。反思的价值在于引入第二个视角， 而不在于验证正确性。代码是否真的更快，反思循环自己不知道。

二、没有目标函数，就会震荡。评审员被要求「必须找出瓶颈」，于是永远能找出新问题； 改进方向由最后一句话决定，而不是由一组测试决定。v3 到 v4 的回退，正是这种机制的产物。

三、上下文越长越要小心。这里只把「最近一版代码」交给评审，看起来是简化， 实际是省 token 的必然选择——如果把 4 版代码全塞进去，第三轮的单次 prompt 就会翻倍。

想做对比实验，最小改动是：把 max_iterations 设为 1，看只反思一次的结果是否已经接近终稿； 再把 get_trajectory() 接进 refine 提示词，观察震荡是否减少。 两次运行、四组数据，足够写一节实验记录了。
