01

先建立心智模型

asyncio 里没有"并行执行多个函数"这回事，只有一个线程、一个事件循环、一堆可以暂停的函数。 所有并发收益都来自一句话：等待 IO 的时候，把 CPU 让给别人用。

协程（coroutine）是"能在中途暂停的函数"，暂停点就是 await。 每次 await 一个「真的会等」的东西（网络、磁盘、sleep、锁）， 当前协程就把控制权交回事件循环，循环立刻去跑其他就绪的协程； 等 IO 完成，循环再回来从暂停的那一行继续。

这也解释了两条铁律：纯 CPU 计算不会让出（代码里没有 await 就一直占着循环）， 同步阻塞调用会冻住整个循环（不只是冻住自己）。后者正是 _call_tool() 要区分协程和普通函数的原因。

对比项线程（threading）协程（asyncio）
调度者操作系统，抢占式事件循环，协作式（自觉 await）
切换成本微秒级，需保存寄存器/栈纳秒级，就是一次函数调用
内存每线程 MB 级栈每个 Task 一个对象，KB 级
数据竞争需要锁同一时刻只有一段代码在跑，除非跨 await 共享状态
取消无法安全取消一级公民：Task.cancel()

02

协程 · Task · Future 三层对象

搞混这三者，就读不懂 gather 为什么能让事情"同时"发生。 一句话区分：协程是菜谱，Task 是下了单的订单，Future 是取餐号。 

# L266-L272　arun() 里的并发入口
unique: dict[tuple[str, str], ActionCall] = {}
for action in parsed.actions:
    unique.setdefault((action.tool_name, action.tool_input), action)

keys = list(unique)
executed = await asyncio.gather(
    *(self._execute_action(unique[key]) for key in keys)
)

L266–L272 · gather 一次性接管多个协程

生成器表达式里的 self._execute_action(...) 只是创建了协程对象，一行都没有执行。 调用 async def 函数不会运行函数体，这跟普通函数完全不同。

gather 收到这堆协程后，内部用 ensure_future() 把它们逐个包成 Task 并注册到事件循环的 ready 队列——从这一刻起，它们才真正"排上了队"。

随后 gather 自己 await 一个内部 Future， 于是 arun() 这个 Task 挂起，循环开始轮流运行那 4 个子 Task。

对象是什么本例中的角色
coroutine调用 async def 得到的对象，未执行、不能取消_execute_action(action) 的返回值，4 个
Task被注册进事件循环的协程，可取消、可查状态、可加回调gather 内部包出来的 4 个子任务
Future结果占位符，Task 是它的子类Semaphore 排队时等的那个"座位号"
常见误解：await 一个协程 ≠ 开一个 Task。 _call_tool() 里的 await func(**kwargs)（L449）是在当前 Task 内部直接跑完这个协程， 并没有新建任务。只有 gather / create_task 才会包装成独立 Task。
03

挂起点逐个解剖

下面四段是代码里真正会"停"的地方。每段都按进入前 → 挂起时 → 恢复后三段说， 并对上事件循环里发生的事。代码块保留源码原文，过长行可横向滚动。

3.1信号量：唯一会"排队"的地方

# L328-L337　_execute_action()
async def _execute_action(self, action: ActionCall) -> ToolObservation:
    assert self._semaphore is not None, "请通过 arun() 启动，semaphore 在运行时创建"
    async with self._semaphore:                # ← 可能挂起
        return await self._execute_with_retry(action)

L336：async with 的 __aenter__ 就是一次 acquire()。长行可横向滚动。

进入前：acquire() 先看计数。max_concurrency=2 时前两个直接减一返回， 一次 await 都没发生——它们在同一个循环周期里一路跑到工具的 IO 点。

挂起时：第 3 个调用发现计数为 0，循环把当前 Task 塞进 Semaphore 内部的等待队列（FIFO deque）， 并创建一个 Future 给它"取号"，然后挂起。这个挂起不占线程、不耗 CPU、不计入 tool_timeout（见第 05 节）。

恢复后：有人 release()，循环把队列头那个 Future 设为完成，对应 Task 回到 ready 队列， 在 acquire() 的 await 处醒来，继续执行 _execute_with_retry()。

3.2工具执行：只有两个真正的等待形态

# L432-L455　_call_tool()
kwargs = args.model_dump() if args is not None else {}
if inspect.iscoroutinefunction(func):
    # 形态 A：协程工具，直接在当前 Task 里跑
    result = await func(**kwargs) if args is not None else await func(raw_input)
elif args is not None:
    # 形态 B：同步函数，丢给线程池
    result = await asyncio.to_thread(func, **kwargs)
else:
    result = await asyncio.to_thread(func, raw_input)

L447–L455：同一行 await，两种完全不同的语义

形态 A（协程，如 asearch）：不新建 Task，就在当前 Task 的栈里执行。 挂起点在工具内部第一次真正的 IO await（await client.post(...)）。 工具挂起时，本 Task 的其他代码也一起暂停，这正是我们想要的。

形态 B（同步，如老的 SerpApi 版 search）：把函数丢进默认线程池， 当前 Task 挂起等一个 executor Future。线程里跑的是真并行，而事件循环不受影响。

统一成 str 返回后，两种形态对上层完全透明——这是 ToolObservation 能一视同仁的前提。

3.3模型调用：流式响应会反复挂起

# L298-L326　_think()
async with asyncio.timeout(self.config.llm_timeout):   # 只注册定时器，不挂起
    athink = getattr(self.llm_client, "athink", None)
    if athink is None:
        return await asyncio.to_thread(self.llm_client.think, messages=messages)
    return await athink(messages=messages)              # ← 挂起

# chapter4.py　athink() 内部
async for chunk in stream:        # 每来一块数据，挂起一次、恢复一次
    content = chunk.choices[0].delta.content or ""

L309–L314 + chapter4.py · 流式调用的挂起节奏

async with asyncio.timeout(...) 进入时只是往循环里注册一个定时器，不会挂起。 真正挂起发生在内部的 await。

流式响应很有意思：它不是"挂起一次拿回全部结果"，而是 每个 chunk 挂起一次、恢复一次。所以模型一边输出，循环一边还能跑别的就绪任务——这也是同一个 Agent 里 print 能实时打出字的原因。

代价是：llm_timeout 覆盖的是整个流，不是单个 chunk。流到一半超时，会直接取消整个流并降级。

3.4重试退避：等待也要有上界

# L417-L421
if attempt <= self.config.tool_retries:
    delay = 0.5 * attempt
    print(f"↻ {delay}s 后重试")
    async with asyncio.timeout(delay + 1.0):   # 退避等待也要有上界
        await asyncio.sleep(delay)

L420：故意给 sleep 也套一层 timeout

await asyncio.sleep(delay) 是最干净的挂起点：没有副作用，就是告诉循环"delay 秒后叫我"。

外面再套一层 timeout(delay + 1.0) 看起来多余，实际是防御： 如果此处被外部取消，sleep 会立刻抛 CancelledError 而不是傻等， 取消不会因为"正在退避"而被拖住。

顺带解释了"为什么失败也要写回 history"：Boom 的失败是一条普通 Observation， 模型在第 2 步能看到它，从而不再重复调用同一个坏工具。异常处理的边界设在单个 Tool 内， 整个 ReAct 循环的连续性才有保障。
05

信号量排队：为什么排队不计入超时

这段顺序是有讲究的：timeout 在 semaphore 里面。 换成相反的顺序，排在队尾的调用会被误判为"超时"，而它其实一次都没跑过。

当前写法（正确）

async with self._semaphore:                       # 先排队
    async with asyncio.timeout(tool_timeout):     # 拿到名额才开始计时
        await self._call_tool(...)

排队多久都不影响 tool_timeout，计时只覆盖"真正占有资源"的那段时间。

反例（会误伤）

async with asyncio.timeout(tool_timeout):     # 排队时间也算进去
    async with self._semaphore:
        await self._call_tool(...)

并发上限 3、排队 30s → 第 4 个调用在拿到名额前就"超时"， 报错信息会误导人去查工具本身。

还有一个容易忽略的点：asyncio.Semaphore 的等待队列是 FIFO。 因为 gather 按列表顺序创建 Task，所以执行顺序基本等于模型书写顺序 （实测中 Boom[三] 在 0.15 接棒、Fast[四] 在 0.36 接棒，顺序完全没乱）。

但这里有个微妙之处：acquire() 成功的那两个 Task 并非"同时"开始， 而是事件循环依次调度、各自跑到第一个 IO await 就挂起。所以严格说是近乎同时，不是真并行。

参数控制什么调大之后调小之后
max_concurrency同时持有名额的工具数并发更高，但外部 API 更容易触发限流（DeepSeek Search 是 100 QPS）更保守，轮次变慢
tool_timeout单次工具执行的净耗时上限慢工具能跑完，但一轮可能被拖很久容易把正常但较慢的工具取消掉
tool_retries失败后的额外尝试次数容错更强，计费型工具会多花钱更快降级
06

超时就是取消：asyncio.timeout 做了什么

asyncio.timeout() 不是"中断执行"，而是"到点往当前 Task 里塞一个取消信号"。 理解这一点，才能理解后面所有的异常处理顺序。

1
进入 with：注册定时器

__aenter__ 调 loop.call_at(deadline, ...) 挂一个 TimerHandle，不挂起、不阻塞。

↓
2
内部 await：Task 挂起

执行到 await self._call_tool(...)（L384），Task 让出控制权，循环去跑别的任务。

↓
3
到点：Task.cancel()

定时器触发，循环对当前 Task 调 cancel()。它只是在挂起点抛 CancelledError，不会强行杀线程。

↓
4
退出 with：翻译成 TimeoutError

__aexit__ 发现自己是"因超时而取消"，把 CancelledError 换成 TimeoutError 抛出。

↓
5
业务代码接住：except TimeoutError

在 L392–L394 记下 status="timeout"，进入重试或降级分支。超时因此变成一条普通 Observation。

# L383-L421　两处 timeout 的位置
try:
    async with asyncio.timeout(self.config.tool_timeout):   # 每次尝试单独计时
        output = await self._call_tool(func, args, action.tool_input)
    return ToolObservation(status="ok", ...)
except TimeoutError:
    status = "timeout"
    last_error = f"执行超时（>{self.config.tool_timeout}s）"
except asyncio.CancelledError:
    raise                                # 取消不是工具失败

注意：两个分支必须分开写，见下方说明

为什么 except Exception 抓不到取消？ Python 3.8 起 CancelledError 直接继承 BaseException， 就是为了防止被人顺手写个 except Exception 吞掉。

代码里仍然显式写了 except asyncio.CancelledError: raise， 这是表达意图：告诉读代码的人"这里知道有取消，且选择继续往上抛"， 而不是靠语言特性意外生效。

如果把它改成 except Exception 并且返回降级结果，会发生什么？ 外部取消被当成"工具失败"，gather 收不到取消信号， 整轮会继续跑完——用户按 Ctrl+C 之后程序还在发请求，这是最难查的一类 bug。

一个细节：每次重试都在 for 循环里重新 async with asyncio.timeout(...)， 所以计时器是每次尝试独立的。若把 timeout 提到循环外面，两次尝试共用一份额度， 第二次尝试可能刚发出就被取消。
07

to_thread：唯一的真并行

asyncio.to_thread() 把同步函数丢进默认线程池（run_in_executor 的封装）。 这是整份实现里唯一会出现"两个函数同时占 CPU"的地方——也带来唯一无法根治的缺陷。 

# L447-L455
if inspect.iscoroutinefunction(func):
    result = await func(**kwargs)
elif args is not None:
    result = await asyncio.to_thread(func, **kwargs)   # 线程池
else:
    result = await asyncio.to_thread(func, raw_input)
return result if isinstance(result, str) else str(result)

L449–L455 · 协程走 await，同步走线程池

不丢线程池会怎样？同步的 search() 直接调用会在事件循环线程里阻塞。 那一刻所有 Task 都停住：其他工具没机会跑、gather 退化成串行、 连超时定时器都没法触发（因为循环本身被卡住了）。所以 tool_timeout 也会失效。

代价：timeout 到期只是让协程"不再等"，线程还在后台跑完。 对 HTTP 调用通常无害（最多浪费一次请求），但绝不能把死循环放进 to_thread—— 线程池名额会被永久占住，默认池只有 min(32, cpu+4) 个位置。

协程工具（asearch）同步工具（旧 search）
执行位置事件循环线程线程池线程
并发方式挂起切换真并行
超时生效精确，挂起点立即抛 CancelledError只能"不再等"，线程继续跑完
CPU 密集会卡住整个循环受 GIL 限制，但至少不卡循环
推荐首选（DeepSeek Search 已改为 asearch）兼容存量同步工具
顺带一提：to_thread 的排队不在 Semaphore 的管辖范围内。 如果并发上限设得比线程池大，工具会在两个队列里各排一次——排查"为什么没超时却迟迟不开始"时要想到这点。
08

取消如何一路向上

一次外部取消（快捷键、上层 wait_for、服务关闭）要走完四层才能退出。 这条链路上有两件事必须成立：信号不被吞，资源不泄漏。

1
外部发起取消

例如 asyncio.wait_for(agent.arun(q), 0.2) 超时，或收到 SIGINT。

↓
2
arun() 在 await gather 处被唤醒

gather 收到 CancelledError 后，会转发给所有子 Task，然后自身抛出取消。

↓
3
子 Task 在挂起点收到取消

正在 await asyncio.sleep() / await client.post() 的工具立即被中断。

↓
4
穿过 _execute_with_retry 与 _execute_action

except asyncio.CancelledError: raise 原样上抛；async with self._semaphore 的 __aexit__ 仍然执行，名额被正确归还。

↓
5
arun() 不捕获，直接退出

没有 except CancelledError，也没有 finally 里再 await 别的东西， 所以取消能干净地传回调用方。

资源不泄漏的关键

  • async with 在异常/取消路径上同样执行 __aexit__，所以 release() 不会漏
  • 如果取消发生在 acquire() 时，__aenter__ 就没完成，__aexit__ 不会执行，也不会错误地多释放一次
  • Semaphore 每次 arun() 重建，天然没有跨循环残留

会破坏取消的三件事

  • 用 except Exception 接住取消并返回正常值
  • 在 except 里再 await 一个长任务（此时取消已生效，会立刻二次抛出）
  • 用 gather(..., return_exceptions=True) 后把 CancelledError 当成普通异常收集
09

这份实现里的坑清单

都是写异步代码时真会踩到的，按"踩中的后果"排。

陷阱后果本实现的处理
调用 async def 忘了 await 拿到一个协程对象，函数体压根不执行，还报 "coroutine was never awaited" _call_tool 先 iscoroutinefunction 判断，两种形态都显式 await
同步函数直接在循环里调 整个事件循环冻结，超时定时器也停摆 统一走 asyncio.to_thread
在 __init__ 里建 Semaphore 第二次 asyncio.run() 时跨事件循环报错 在 arun() 开头重建
timeout 包在 semaphore 外面 排队时间被算进超时，误判正常调用 timeout 放在 async with semaphore 内部
超时与取消共用一个 except 外部取消被当成工具失败，程序停不下来 except TimeoutError 与 except CancelledError: raise 分开写
把整个 Task 重试 已成功的部分被重复执行，计费工具白花钱 重试粒度是单次工具调用，且在参数校验之后
gather 里放会抛异常的裸协程 一个失败让整轮 gather 直接抛，其他结果全丢 _execute_with_retry 保证不抛（除取消），失败变成 Observation
同轮重复 query 全量计费 模型常写 3 条语义相同的搜索，付 3 次钱 按 (工具名, 原始输入) 去重 + Search 层 TTL 缓存
CPU 死循环放进 to_thread 线程池名额被永久占用，后续工具排队排队再排队 文档里明确标注不适用；CPU 计算本就不该进工具
