PLAN & SOLVE · 结构说明

先规划，后执行：一条两段式的推理流水线

这个 Agent 不做边想边试的搜索。它先把问题拆成一份步骤清单， 再让每一步只填一个空。以下文档按「入口 → 规划 → 解析 → 执行 → 输出」的顺序， 说明三个类各自的职责、数据的形态变化，以及几个必须注意的分支。

01 / 功能概述

它解决什么问题

Plan-and-Solve 的思路是把「想」和「做」拆开：先让模型输出一份结构化的步骤清单， 再让模型逐步执行、每步只回答当前子任务。相比 ReAct 的「边想边搜」，它没有工具调用、也没有回溯， 优势是方向一次定好、成本可预测，劣势是计划错了不会纠偏。

维度说明
输入一个问题字符串 question，来自命令行参数或内置默认示例
输出最后一步的执行结果 final_answer，由 run() 打印；函数本身不返回
中间产物计划列表 plan: list[str] 与累积上下文 history: str
外部依赖HelloAgentsLLM（封装 OpenAI 接口，默认 DeepSeek）、python-dotenv、ast 标准库
不使用工具全程无搜索、无网络请求，只依赖模型自身知识
02 / 模块职责

三个类，各管一段

顶层类只做「编排」，两个子类各管一个阶段。三者共享同一个 LLM 客户端实例，因此配置与连接只初始化一次。

CLASS 01

PlanAndSolveAgent

编排者

持有客户端，构造时创建 Planner 与 Executor；run() 串起「规划 → 检查 → 执行 → 打印」。

输入
question: str
方法
run()：先 plan()，空则终止，否则 execute()
注意
无返回值，答案只在 print 里
CLASS 02

Planner

规划者 · 1 次调用

把问题变成步骤清单。要求模型输出带 ```python 围栏的 Python 列表字面量，然后用 ast.literal_eval 安全解析。

输入
question → 填入 PLANNER_PROMPT_TEMPLATE
输出
list[str]，失败时返回空列表 []
风险点
模型漏写围栏、括号不闭合、返回非列表
CLASS 03

Executor

执行者 · N 次调用

按顺序遍历计划，每一步都把「原题 + 完整计划 + 已完成结果 + 当前步骤」拼成新 prompt，只索取当前步骤的答案。

输入
question、plan
输出
最后一步的响应 str
关键状态
history 字符串逐步累加
109class PlanAndSolveAgent:
110    def __init__(self, llm_client):
115        self.planner  = Planner(self.llm_client)
116        self.executor = Executor(self.llm_client)
118    def run(self, question: str):
125        plan = self.planner.plan(question)
128        if not plan:                      # 空计划 → 直接终止
129            print("\n--- 任务终止 --- \n无法生成有效的行动计划。")
130            return
133        final_answer = self.executor.execute(question, plan)

注意 run() 的两个 print 之间没有 return final_answer——这是当前实现的一个局限，见文末说明。

03 / 执行流程

从入口到结束，共 8 步

按代码实际执行顺序排列。编号 S1–S8 与「数据流转」一节的阶段一一对应。

  1. S1

    解释器找到入口

    L154–L155 · if __name__ == "__main__"

    只有直接运行（python -m uv_and_httpx.PlanAndSolveAgent）才调用 main()；被 import 时什么都不发生。

  2. S2

    构造 LLM 客户端

    main() · L139

    HelloAgentsLLM() 读取环境变量，默认 base_url=https://api.deepseek.com、model=deepseek-flash，并关闭 thinking 模式。

    → OpenAI 客户端实例
  3. S3

    组装智能体

    L142 · PlanAndSolveAgent(llm_client)

    构造函数内部立刻 new 出两个子组件，并把同一个客户端引用传给它们——共享连接、共享配置。

    → agent.planner / agent.executor
  4. S4

    确定问题文本

    L147 · sys.argv[1:]

    命令行有参数就拼接使用，否则回落到常量 DEFAULT_QUESTION（那道容斥原理题）。

    → question: str
  5. S5

    规划：把问题拆成清单

    Planner.plan() · L44–L72

    ① 用 PLANNER_PROMPT_TEMPLATE.format(question=…) 生成提示词；
    ② 包成单条 user 消息调用 think()，得到纯文本；
    ③ response_text.split("```python")[1].split("```")[0] 取出代码块内容；
    ④ ast.literal_eval() 把它安全地还原成 Python 列表。

    → plan: list[str]（渲染图里的竖向清单）
  6. S6

    分支：计划是否为空

    L128–L130

    解析失败或模型返回非列表时，plan 为 []，此处打印「任务终止」并 return，不进入执行阶段。

    → 提前结束（无异常抛出）
  7. S7

    执行：逐步填空

    Executor.execute() · L78–L107

    对每一步 step：把原题、完整计划、history 与 current_step 一起塞进执行模板， 调用模型后只取这一步的结果，随后 history += "步骤 i: …\n结果: …"，把结果交给下一步。

    → 每一步一次模型调用，共 N 次
  8. S8

    收尾：最后一步的输出即答案

    L105–L107 · L135

    循环结束后 final_answer = response_text，run() 打印「任务完成 + 最终答案」，程序退出。整个过程没有再调用模型做汇总。

    → 控制台输出，函数返回 None
04 / 数据流转

一个字符串，四次变形

整条流水线的核心是「文本 → 结构 → 文本」的往返。下表列出每个阶段的载体变量、类型与形态。

阶段变量类型形态 / 示例
S4 输入questionstr 某班级共 40 人，其中 60% 喜欢数学……
S5 提示词promptstr 模板 + 问题，要求输出 ```python [...] ```
S5 原始响应response_textstr 带围栏的多行文本（含解释性文字）
S5 解析后planlist[str] ["计算…24人", "计算…20人", …]
S7 累积上下文historystr 每轮追加 步骤 i: … / 结果: …，只增不减
S8 输出final_answerstr 仅最后一步的响应，例如 40 - 32 = 8人

history 是如何长出来的

history 是一个不断变长的字符串，第二轮起它就成为模型「记得前面做过什么」的唯一途径。 下面是执行到第 3 步时它的真实内容： 

# 第 1 步结束后
步骤 1: 计算班级总人数40人中喜欢数学的人数：40 * 60% = 24人
结果: 40 * 60% = 24人

# 第 2 步结束后（注意是追加，不是覆盖）
步骤 1: 计算班级总人数40人中喜欢数学的人数：40 * 60% = 24人
结果: 40 * 60% = 24人

步骤 2: 计算班级总人数40人中喜欢物理的人数：40 * 50% = 20人
结果: 40 * 50% = 20人

# 第 3 步结束后
… 步骤 3: 确定两门都喜欢的人数为：40 * 30% = 12人
结果: 40 * 30% = 12人
注意 history if history else "无"： 第一步时字符串为空，直接填进模板会留下空白段，所以代码在空串时替换成「无」，让 prompt 结构保持完整。
05 / 分支与依赖

五个必须知道的分支

这些分支决定了「崩掉」还是「优雅地失败」。LLM 输出不可控，防御全在这一层。

没找到 ```python 围栏

split(...)[1] 抛 IndexError，被捕获 → 返回 [] → 上层终止。

用 or "" 先把 None 变成空串，避免 None.split() 直接崩在类型错误上。

列表语法不合法

ast.literal_eval 抛 ValueError / SyntaxError，打印原始响应后返回 []。

用 literal_eval 而不是 eval：只解析字面量，不可能执行任意代码。

解析结果是别的类型

return plan if isinstance(plan, list) else [] 兜住「模型给了个字典或字符串」。

保证 plan 恒为 list[str]，下游 enumerate 才不会拿到字符。

计划为空列表

run() 打印「无法生成有效的行动计划」并 return，不抛异常。

这是唯一的「软失败」出口；调用方无法通过异常感知失败，只能看日志。

最后一步即最终答案

final_answer = response_text，不额外调用模型做汇总。

省一次调用，但要求计划本身把「得出结论」放在最后一步——这是 prompt 设计的一部分。

依赖调用链

# 一次完整的调用栈（执行阶段）
main()
└─ agent.run(question)
   ├─ Planner.plan()
   │   └─ llm_client.think(messages)        # openai SDK → DeepSeek /chat/completions
   │       └─ ast.literal_eval(...)          # 文本 → list[str]
   └─ Executor.execute(question, plan)
       └─ for step in plan:
           └─ llm_client.think(messages)     # 每步一次请求，携带 history

模型调用全部经由 HelloAgentsLLM.think()——它内部使用 stream=True 边接收边打印，最后把片段拼成完整字符串返回，所以上层拿到的是纯文本而不是响应对象。

06 / 实测样本

真实跑一次的记录

默认问题：某班级共 40 人，60% 喜欢数学，50% 喜欢物理，30% 两门都喜欢——两门都不喜欢的有多少人？ 本次模型规划出 5 步，共 6 次调用。

S5 规划：1 次调用，返回 5 条步骤 plan[5]
S7.1 计算喜欢数学的人数：40 * 60% 24 人
S7.2 计算喜欢物理的人数：40 * 50% 20 人
S7.3 确定两门都喜欢的人数：40 * 30% 12 人
S7.4 容斥原理：至少喜欢一门 = 24 + 20 − 12 32 人
S7.5 两门都不喜欢 = 40 − 32 8 人
FINAL ANSWER · S8 40 - 32 = 8人
两次运行的步数并不固定：首次测试生成了 6 步（多了一条「验证结果合理性」），本次只有 5 步。 这说明计划长度完全由模型决定，max_steps 这类上限在当前实现里并不存在——步数越多，调用次数与耗时越多。
