01

全局视图

ReActAgent 本身不写提示词、不发请求、不搜网页， 它只做一件事：把三样东西串成一个循环——拼提示、问模型、执行动作。 真正的脏活由两个协作者承担。

模型层 HelloAgentsLLM

封装 OpenAI 兼容接口，默认指向 DeepSeek。负责流式调用并返回纯文本。

→
编排层 ReActAgent

持有 history，循环「拼提示 → 问模型 → 解析 → 执行」，直到 Finish 或步数耗尽。

→
工具层 ToolExecutor

登记工具名 → 函数的映射；Search 背后是 SerpApi 真实搜索。

输入
一个自然语言问题，例如 "英伟达最新的GPU型号是什么"
输出
模型给出的最终答案字符串；中途失败则返回 None
关键状态
self.history —— 一个纯字符串列表，累积每轮的 Action 与 Observation，下一轮原样拼回提示词

准备：依赖与提示词模板L1–L26

模块级常量 · 全局共享一份

1import re
2
3from uv_and_httpx.ToolExecutor import ToolExecutor
4from uv_and_httpx.chapter4 import HelloAgentsLLM
5from openai.types.chat import ChatCompletionMessageParam

9REACT_PROMPT_TEMPLATE = """
Thought: 你的思考过程…
Action: 你决定采取的行动…
  - 工具名[参数]  或  Finish[最终答案]
Question: {question}
History: {history}
"""

模板是整个 Agent 的「行为契约」：它告诉模型必须先想再动，且只能输出两种动作形态。 {tools}、{question}、{history} 三个占位符留给 .format() 填； 而 {{tool_name}} 用双花括号，是刻意转义成字面量，留给模型看格式，Python 不会去替换它。

作用
把「推理格式」固化成文本约定，模型只需照着填
输出
一个带 3 个命名占位符的字符串常量

构造：注入两个协作者L30–L34

依赖注入 · 不在内部 new

30def __init__(self, llm_client: HelloAgentsLLM,
31             tool_executor: ToolExecutor, max_steps: int = 5):
32    self.llm_client = llm_client
33    self.tool_executor = tool_executor
34    self.max_steps = max_steps
35    self.history = []          # 跨轮次的唯一记忆

模型和工具箱都是从外部传进来的，这样测试时可以塞假模型、换真搜索为 mock， 而不用改 Agent 一行代码。这就是「依赖注入」最朴素的样子。

为什么 history 是 list[str] 而不是 messages？ 因为每一轮都把历史塞进同一条 user 提示词里，而不是维护多轮对话。 写法简单、可读，代价是 token 随轮次线性增长。

解析输出：两个正则各管一段L109–L121 · 在流程图中查看 →

_parse_output() · 把自由文本切成 Thought / Action

113thought_match = re.search(r"Thought:\s*(.*?)(?=\nAction:|$)", text, re.DOTALL)
115action_match  = re.search(r"Action:\s*(Finish\[.*\]|\w+\[.*?\])", text, re.DOTALL)
116
117thought = thought_match.group(1).strip() if thought_match else None
118action  = action_match.group(1).strip()  if action_match  else None

Thought 用前瞻断言 (?=\nAction:|$) 截到 Action 之前； Action 则限定只能匹配两种形态，绝不贪婪到文末。

这里曾是最严重的 bug：旧写法 r"Action:\s*(.*?)$" 配合 re.DOTALL， 为了满足行尾锚点会一路扩到字符串末尾，把后面的 Observation、第二个 Thought、 甚至 Finish[…] 全部吞进工具参数，导致拿着脏参数去搜索。
输入
模型返回的整段文本
输出
二元组 (thought, action)，任一可能为 None

Finish 分支：收尾并返回L75–L85 · 在流程图中查看 →

成功出口 · 唯一 return 答案的地方

75if action.startswith("Finish"):
78    finish_match = re.match(r"Finish\[(.*)\]", action, re.DOTALL)
79    if finish_match:
80        final_answer = finish_match.group(1).strip()
81    else:
83        final_answer = action.removeprefix("Finish").strip().strip("[]`")
85    return final_answer

三步防御：① DOTALL 让答案能跨行；② 判空，匹配失败不能直接 .group(1)； ③ 兜底，容忍模型写成 Finish[答案 缺右括号或带反引号的情况。

输入
以 Finish 开头的 action 字符串
输出
剥离标记后的最终答案，直接 return 跳出 run()
⑤

解析工具调用并执行L87–L99 · 在流程图中查看 →

_parse_action() → getTool() → 真正调用

87tool_name, tool_input = self._parse_action(action)
88if not tool_name or not tool_input:
90    continue                    # 解析失败 → 下一轮
92
94tool_function = self.tool_executor.getTool(tool_name)

_parse_action 用 (\w+)\[(.*)\] 把 Search[关键词] 拆成名字和参数。 模型只负责给参数，执行发生在本地——这是 Agent 安全模型的根基： 模型无权直接触达网络，它只能"申请"一次调用。

输入
形如 Search[英伟达最新GPU型号 2025] 的 action
输出
工具返回的字符串 observation（或错误提示）

回写历史：让下一轮"记得"L101–L103 · 在流程图中查看 →

整个循环唯一的状态变更点

102self.history.append(f"Action: {action}")
103self.history.append(f"Observation: {observation}")

这两行是 ReAct 的心脏。下一轮 ① 会把它们拼回提示词，模型于是看到"我上一步做了什么、得到了什么"， 再决定是继续查、还是收尾。没有这两行，循环就退化成反复问同一个问题。

输入
本轮的 action 与 observation
输出
history 变长两项 → 回到 ①
⑦

三种终止方式：④ Finish（成功，返回答案）、②③ 的空值检查（失败，break）、 ⑦ 步数耗尽（兜底，返回 None）。max_steps 是防死循环和防烧钱的刹车片。

05

三个关键细节

这三处决定了这个 Agent 是"能跑"还是"稳跑"。

DETAIL 01

DOTALL：让点号吃掉换行

默认 . 不匹配 \n，而 LLM 答案天然跨行。 re.DOTALL 等于 (?s)，不加就会在多行内容上匹配失败、返回 None。

DETAIL 02

判空：Match 可能是 None

re.search/match 的返回类型是 Match | None。 不判空直接 .group()，就是把自己交给 AttributeError—— 用 # pyright: ignore 只会遮住警告，不会拦住崩溃。

DETAIL 03

一次一步：别让模型抢跑

即使模型在同一条响应里既给了 Search 又给了 Finish，循环也只执行第一个。 这保证了每步都有真实的 Observation 作为证据，而不是让模型凭空收尾。

下一步可以做的事： 把解析失败的信息也写进 history（而不是静默 continue）， 模型才能看到自己的格式错误并自我纠正；另外在 _parse_action 开头清洗反引号，防止模型照抄模板里的 `工具名[参数]`。
