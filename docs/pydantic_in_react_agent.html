数据流全景

在这个项目里，Pydantic 既不是 ORM，也不是序列化框架。它只干一件事： 站在"不可信数据"和"业务逻辑"之间，做类型化的闸门。

闸门 ②

2.1策略参数都是什么意思

上面那张表里的每个词都能单独生效，也能组合。阅读重点是最后两列： 本项目用在哪（知道该去哪改）、不写会怎样（大部分坑都来自默认值）。

参数含义本项目用在哪不写会怎样
模型级 · 写在 model_config · ConfigDict(...) 里，对整张模型生效
frozen=True 实例创建后字段不可再赋值；改了会抛 ValidationError: Instance is frozen（不是 AttributeError） AgentConfig、ActionCall 运行途中谁都能改配置；gather 并发时"读到一半被改"的状态无法推理
extra="forbid" 出现没声明过的字段就报 Extra inputs are not permitted AgentConfig、ToolArgs、SearchRequest 默认是 "ignore"：AgentConfig(max_concurreny=2) 拼错字段会静默失效，并发上限还是 3
extra="ignore" 多余字段直接丢弃，不报错、也不保留 SearchResultItem、SearchResponse 它本身就是默认值；显式写出来是为了表明"这里预期会有未知字段"
str_strip_whitespace=True 所有 str 字段先去掉首尾空白，再做长度 / pattern 校验；对嵌套模型同样生效 ToolArgs、SearchRequest " " 能通过 min_length=1，变成一个全是空格的查询词打到搜索 API
字段级 · 写在 Field(...) 里，只对该字段生效
min_length / max_length 字符串是字符数；对 list 是元素个数（报错文案会变成 at most 2 items） SearchArgs.query 2–128；ActionCall.tool_name 1–64、tool_input 1–4000 任意长度都能进工具，超长 query 直接被 API 400 拒掉
ge / gt / le / lt 数值边界：≥ / > / ≤ / <。报错文案会对应用词（greater than 0、less than or equal to 16） max_steps 1–20、max_concurrency 1–16、tool_timeout 0–300、tool_retries 0–3 max_steps=999 也能构造出来，跑一轮 ReAct 会烧掉 999 次模型调用
pattern="^\w+$" 正则校验。注意它是 re.search 语义，不是全字符串匹配，所以必须自带 ^ $ 锚点 ActionCall.tool_name 若只写 \w+，"Bad Name" 也能通过（匹配到 "Bad" 就算命中）
默认值（= "" / = -1 / = 0.0） 字段缺失时用它补齐，而不是报 Field required SearchResultItem 全部字段；ToolObservation.attempts = 0 缺一个字段就 KeyError / 校验失败，整次搜索结果报废
类型级 · 靠类型标注本身表达约束
Literal["ok", ...] 值必须命中其中一个字面量；报错时会把全部合法值列出来 ToolObservation.status 的 5 个值 写成普通 str，拼错 "failed" 也能存进去，status == "ok" 的判断就永远对不上
str | None = None 可选字段，允许不传 SearchRequest.ori_question、SearchResultItem.site_name 不传就报 Field required；且无法用 exclude_none 在出站时省掉它
配套方法 · 不是参数，但总跟这些策略一起出现
fromToolInput() 自定义适配器：把 ReAct 的原始文本按"单字段 / 多字段"分流，再交给 model_validate 或 model_validate_json ToolArgs（各工具共用一份） 每个工具都要自己写一遍"文本怎么变成参数"，而且容易漏掉 JSON 解析失败的处理
model_validate() / model_validate_json() 从 dict / JSON 文本构造并校验（v2 写法，对应 v1 的 parse_obj / parse_raw） ToolArgs.fromToolInput、search._parse_payload 直接用 Model(**dict) 也行，但拿不到 JSON 文本入口
model_dump(exclude_none=True) 导出成 dict，并丢掉值为 None 的键 SearchRequest.payload() 请求体里会带上 "ori_question": null，多传一个字段给服务端
model_copy(update=...) 浅复制并替换字段，不校验 ReActAgent.__init__ L196（兼容旧 max_steps 参数） 这是唯一会绕过所有字段约束的入口，详见第 09 节
最容易踩的一个：pattern 是 search 语义。 实测 Field(pattern=r"\w+") 对 "Bad Name" 通过（字符串里能找到 "Bad" 就算命中）， 必须写成 ^\w+$ 才拦得住。这和很多人以为的"整串匹配"不一样。
>>> 实测：extra 三态 extra="forbid" + 多余字段 拦截 ('b',) -> Extra inputs are not permitted extra="ignore" + 多余字段 OK Ignore(a=1) ← 丢弃，快照里没有 b extra="allow" + 多余字段 OK model_extra={'b': 2} ← 保留在 model_extra 里 >>> 实测：pattern / strip / 边界 pattern="\w+" + "Bad Name" OK ← search 语义放行 pattern="^\w+$" + "Bad Name" 拦截 String should match pattern '^\w+$' str_strip_whitespace（嵌套模型） OK ' 带空格 ' -> '带空格' frozen=True 后赋值 拦截 ValidationError: Instance is frozen
03

闸门一：ActionCall —— 容忍式校验

模型输出是不可信但可纠正的。所以这一层不追求"全对才放行"，而是"错的丢掉、对的全跑"。 一次格式失误不该让整轮作废。 

# L104-L121　ReActAgent.py
class ActionCall(BaseModel):
    model_config = ConfigDict(frozen=True)

    tool_name: str = Field(min_length=1, max_length=64, pattern=r"^\w+$")
    tool_input: str = Field(min_length=1, max_length=4000)

    @property
    def raw(self) -> str:
        return f"{self.tool_name}[{self.tool_input}]"

约束写在声明处，代码里没有一行 if 判断

三个约束各有明确目的：pattern 拦掉"工具名带空格/中文/标点"这类不可能命中注册表的输入； min_length=1 拦掉 Search[] 这种空参数； max_length=4000 防的是模型把整段 Observation 复制进参数里。

在 parse_response() 里，构造失败只打一行警告并 continue， 同轮其他合法 Action 不受影响——这就是"容忍式"。 

>>> 实测四种输入
Search[hi]                        OK    ActionCall(tool_name='Search', tool_input='hi')
Bad Name[hi]（名字带空格）          丢弃  tool_name: String should match pattern '^\w+$'
Search[]（空参数）                 丢弃  tool_input: String should have at least 1 character
Search[4001 个字符]               丢弃  tool_input: String should have at most 4000 characters
为什么这里不直接抛异常？因为模型经常一轮写 3–5 行 Action，其中一行笔误很常见。 抛异常 → 整轮白跑 + 浪费一次模型调用；丢弃 → 剩下的照常执行，模型下一轮从 history 里看到缺了什么自然会补。
04

闸门二：ToolArgs —— 严格式校验

上一关只保证"工具名像个标识符"；工具真正需要什么参数，只有它自己的模型知道。 这一关不过，工具函数一次都不会被调用。 

# ToolExecutor.py L21-L38　参数模型的基类
class ToolArgs(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)

    @classmethod
    def fromToolInput(cls, raw_input: str) -> Self:
        field_names = list(cls.model_fields)
        if len(field_names) == 1:
            # 单参数工具：Search[英伟达最新GPU] -> {"query": "英伟达最新GPU"}
            return cls.model_validate({field_names[0]: raw_input})
        # 多参数工具：Weather[{"city": "杭州", "unit": "c"}]
        return cls.model_validate_json(raw_input)

L21–L38：两条路径 —— 单字段吃纯文本，多字段吃 JSON

为什么不强制所有工具都写 JSON？因为 ReAct 的文本协议本来就长这样： Action: Search[英伟达最新GPU]。让模型为了一个搜索词去拼 {"query": ...}， 除了增加出错率没有任何收益。所以单参数工具走"整段文本 → 唯一字段"的捷径； 只有真的多参数时才要求 JSON。

调用点只有一处：_execute_with_retry() 的第 ① 步（L363）。 校验通过才继续往下走，失败立刻 return 一条 invalid_args 观察。 

# ReActAgent.py L361-L368　唯一的调用点
# ① 参数校验：不通过直接返回，工具函数绝不执行
try:
    args = self.tool_executor.parseArgs(name, action.tool_input)
except ValidationError as e:
    first = e.errors()[0]
    detail = f"{'.'.join(str(x) for x in first['loc'])}: {first['msg']}"
    return ToolObservation(status="invalid_args", output=f"⛔ 参数校验失败，工具未执行（{detail}）...")

L361–L368：校验失败直接 return，工具函数一行都不会执行

>>> 实测：SearchArgs（单参数）
输入 '   '（纯空格）              拦截 ('query',) -> String should have at least 2 characters
输入 '  英伟达 GPU  '              OK    '英伟达 GPU'      ← strip 在长度校验之前生效
输入 128 个字符                    OK    边界内通过
输入 129 个字符                    拦截 ('query',) -> String should have at most 128 characters

>>> 实测：多参数工具（要求 JSON）
输入 "杭州"（不是 JSON）            拦截 () -> Invalid JSON: expected value at line 1 column 1
输入 {"city":"杭州"}（缺字段）       拦截 ('unit',) -> Field required
输入 {..., "x":1}（多余字段）       拦截 ('x',) -> Extra inputs are not permitted
输入 {"city":"杭州","unit":"c"}    OK    WeatherArgs(city='杭州', unit='c')

校验失败的实际后果

  • attempts=0 —— 工具函数没被调用过（实测日志可查）
  • 不消耗重试次数（参数错误重试也没用）
  • 不产生外部 API 费用
  • 失败信息回填给模型，下一轮它会改写

如果没有这层

  • 超长 query 直接打到搜索 API → 400，白付一次请求
  • 空字符串进工具 → 拿到一堆无意义结果，污染 history
  • 多参数工具收到半截 JSON → TypeError，整轮 gather 崩掉
05

闸门三/四：出站严格，入站宽松

这是整份实现里最有借鉴意义的一条策略：同一个 API 的请求和响应，用两种相反的 extra 策略。

出站：SearchRequest（forbid）

# search.py L49-L60
class SearchRequest(BaseModel):
    model_config = ConfigDict(
        extra="forbid",
        str_strip_whitespace=True,
    )
    query: str = Field(min_length=1, max_length=128)
    count: int = Field(default=5, ge=1, le=50)
    ori_question: str | None = Field(default=None, max_length=128)
    need_content: bool = False

    def payload(self) -> dict[str, Any]:
        return self.model_dump(exclude_none=True)

请求体是我们自己拼的，多一个字段就是 bug——必须立刻炸。 exclude_none=True 顺带避免把 "ori_question": null 发给服务端。

入站：SearchResultItem（ignore）

# search.py L63-L77
class SearchResultItem(BaseModel):
    model_config = ConfigDict(extra="ignore")

    title: str = ""
    url: str = ""
    snippet: str = ""
    summary: str = ""
    content: str = ""
    site_name: str | None = None
    date: str | None = None
    authority: int = -1
    rerank_score: float = 0.0

响应是别人给的：服务端哪天加个 favicon_url，forbid 会让你当天全线报错。 ignore + 默认值 = 加字段不炸、缺字段也不炸。 

>>> 实测：入站响应的容错
model_validate({})                                  OK  results=[]
model_validate({"results": [{"title": "只有标题"}]})  OK  title='只有标题' url='' summary='' authority=-1 rerank_score=0.0
model_validate({"results": [], "unknown": 1})       OK  results=[]          ← 未知字段被忽略

>>> 实测：出站请求体自动裁剪
SearchRequest(query="测试").payload()
→ {'query': '测试', 'count': 5, 'need_content': False}   ← ori_question=None 被排除
SearchRequest(query="测试", ori_question="原始问题", count=3).payload()
→ {'query': '测试', 'count': 3, 'ori_question': '原始问题', 'need_content': False}
判断口诀：数据往哪流，就按哪边的规则。我构造的 → 严格；我不控制的 → 宽松。 两个都用 forbid，或者两个都用 ignore，都会在某一天出问题。
06

三个容易被忽略的开关

frozen / Literal / 默认值 —— 每个都只有一行配置，但都改变了程序行为。

6.1frozen=True：不可变，让状态可推理

AgentConfig 和 ActionCall 都设了 frozen=True。 前者防止运行途中有人改 max_concurrency（并发额度会算错）， 后者防止同一个 Action 在执行过程中被就地改写（gather 拿到的 4 个任务互相独立才好推理）。

代价很小，但要注意一个陷阱：model_copy(update=...) 不做校验。 代码里 L196 用它兼容旧的 max_steps 参数——这留下了一个绕过口，详见第 09 节。

6.2Literal status：让"失败"成为类型的一部分

# L142-L154　ToolObservation
status: Literal["ok", "invalid_args", "not_found", "timeout", "error"]
output: str
attempts: int = 0   # invalid_args / not_found 恒为 0：工具压根没跑

L151–L153 · 状态不是自由字符串，而是五个确定的枚举值

>>> 实测：写错状态名时，Pydantic 会列出全部合法值
ToolObservation(..., status="failed")
拦截 ('status',) -> Input should be 'ok', 'invalid_args', 'not_found', 'timeout' or 'error'

有用的不只是"错了会报错"，而是错误信息里带着可选项。 同样的好处也体现在第 07 节：把 ValidationError 的 msg 直接喂给模型， 模型很容易自行纠正（"哦，只能用这五个词"）。

6.3默认值：把 KeyError 变成可用的空值

如果按字典访问写 item["summary"]，一次缺字段就是 KeyError， 整次搜索报废。SearchResultItem 给每个字段都写了默认值， 于是"少了一半字段"变成"能拼出半条结果"，后续 summary or snippet or content 的降级链才有意义。

但别滥用：关键字段该 required 就 required。SearchRequest.query 没有默认值， 因为缺了它这个请求毫无意义——早失败比晚失败好。

07

校验失败，如何变成模型的"反馈"

这是 Pydantic 在这个流程里最容易被低估的作用：ValidationError 本身就是一份可读的诊断报告， 而 Agent 恰好需要一个"能被模型读懂的失败原因"。

step 1

e.errors()[0]

{'loc': ('query',), 'msg': 'String should have at most 128 characters'}

step 2

拼成一行

query: String should have at most 128 characters

step 3

写进 Observation

⛔ 参数校验失败，工具未执行（…），请修正参数后重试。

step 4

模型下一轮改写

history 里带着这条提示，模型自然地缩短 query

# ReActAgent.py L500-L503　形态层也是同一套打法
except ValidationError as e:
    print(f"⚠️ 忽略非法 Action `{raw}`: {e.errors()[0]['msg']}")

两处捕获点（L364 参数层 / L500 形态层）用的是同一种"读 errors 再转文案"的写法

对比一下：如果校验失败抛的是一个自定义 ValueError("bad args")， 模型拿到"bad args"什么也学不到，下一轮多半会犯同样的错。 Pydantic 的 loc + msg 结构恰好提供了"哪个字段、错在哪、期望是什么"这三件事。
08

如果不用 Pydantic

同一份校验需求，手写大概是这个样子。对比时注意漏了哪些分支——那才是声明式校验真正省心的地方。

手写版（示意）

def parse_args(name, raw):
    model = args_models.get(name)
    if model is None:
        return {"query": raw}
    if model is SearchArgs:
        q = raw.strip()
        if not q:
            raise ValueError("query 不能为空")
        if not (2 <= len(q) <= 128):
            raise ValueError("query 长度 2-128")
        return {"query": q}
    if model is WeatherArgs:
        try:
            data = json.loads(raw)
        except json.JSONDecodeError as e:
            raise ValueError(f"JSON 解析失败: {e}")
        if "city" not in data:
            raise ValueError("缺少 city")
        if "unit" not in data:
            raise ValueError("缺少 unit")
        # 还没查多余字段、类型、strip…
        return data

实际写法

class SearchArgs(ToolArgs):
    query: str = Field(min_length=2, max_length=128)

class WeatherArgs(ToolArgs):
    city: str
    unit: str

# 校验逻辑全在基类一处：
def parseArgs(self, name, raw_input):
    args_model = self.getArgsModel(name)
    if args_model is None:
        return None
    return args_model.fromToolInput(raw_input)
  • 加新工具 = 加一个类，不用改校验代码
  • 多参数要求 JSON、单参数走捷径，逻辑只写一次
  • 错误信息格式统一，不需要每个工具自己编文案
  • 模型声明本身还能复用到文档、OpenAPI、前端表单

边界与成本：Pydantic 不管什么

用对地方比用得多重要。这一节讲三个真实的边界，包括本实现里一个确实会被绕过的校验。

>>> 实测
AgentConfig(max_steps=999)                              拦截 ('max_steps',) -> Input should be less than or equal to 20
AgentConfig().model_copy(update={"max_steps": 999}).max_steps  999   ← 校验被绕过

model_copy 是"浅复制 + 直接替换字段"，不经过校验。 所以 ReActAgent(llm, ex, max_steps=999) 能构造出一个 999 步的 Agent。 想保住校验，用重新构造的方式： 

# 推荐：走一遍校验
config = AgentConfig(**{**(config or AgentConfig()).model_dump(), "max_steps": max_steps})
当前状态的说明：本仓库这一行仍用 model_copy，属于已知的小口子。 实际影响有限——命令行入口传给 ReActAgent 的是已校验的 AgentConfig， 只有直接以关键字传 max_steps= 时才绕过。

9.2它不负责的事

不管什么说明谁该负责
业务语义query="今天天气" 格式全对，但可能根本不是个搜索意图模型 + 提示词
权限与安全模型不会因为 schema 合法就不做危险操作工具层白名单、人工确认
网络与超时校验通过 ≠ 请求会成功asyncio.timeout + ToolError 分类
跨字段逻辑"end_date 必须晚于 start_date" 要写 model_validator显式加校验器

9.3成本与并发注意

开销

  • 单次校验是微秒级，相对一次网络工具调用（几十毫秒起）可以忽略
  • 但别在热循环里对大列表反复 model_validate
  • 批量场景用 TypeAdapter(list[Item]).validate_python(...) 比逐个构造快

并发

  • 模型对象校验后不可变（frozen），跨 Task 传递是安全的
  • 校验是纯 CPU 同步操作，不会挂起——放在 gather 的协程里也不影响调度
  • ValidationError 必须显式捕获，冒到 gather 会让整轮失败
10

三句话总结

如果只记三件事，记这三件。

① 它是信任边界，不是格式化工具

模型输出、外部响应都是不可信输入。Pydantic 的价值在于把它们挡在业务逻辑之外， 而不是"把 dict 转成对象好看一点"。

② 输入严、输出松

自己构造的用 extra="forbid"，别人给的用 extra="ignore" + 默认值。 反过来会两头出事：前者静默失效，后者对方一升级你就挂。

③ 失败信息要能被人和模型读懂

loc + msg 直接转成 Observation 文案，失败就从"中断流程"变成"下一轮的输入"。 这也是整条链路能做到"降级而不中断"的基础。

场景用哪个模型失败后
模型输出解析ActionCall / ReActResponse丢弃该条，同轮继续
工具调用前工具自己的 ToolArgs 子类invalid_args，工具不执行
Agent 启动AgentConfig构造期直接抛 ValidationError
发请求前SearchRequest不该发生；发生即写错代码
收响应后SearchResponse容错；结构完全不对才转 ToolError
